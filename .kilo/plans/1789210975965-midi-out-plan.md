# RTR: configurable MIDI-out + MIDI-in control (goto-zone path-finding, start actions)

## Goal

Two related capabilities, one plan:

1. **MIDI-out** (`rtr/sound/sound.py`): extend the existing zone→note / mode→CC adapter
   into a full, **configurable, data-driven** MIDI-out. A new `sound.json` holds the
   mapping (served/saved over the same HTTP API as `zones.json`, hot-reloaded, editable
   in `editor.html`). Triggers: **zone entry, action start, per-pose steps**.
2. **MIDI-in** (`rtr/io/midi.py`): let a MIDI controller command the robot the same way
   the client does — **`goto_zone`** (enhanced to find a **multi-hop path** through the
   zone graph via intermediate zones' exit poses) and **`play_action`** (start actions,
   which MIDI cannot do today).

## Decisions (resolved with user)

- **Direction:** both sides in one plan (MIDI-in control + MIDI-out extension).
- **MIDI-out** = extend `sound.py` (single MIDI-out channel), data-driven from `sound.json`.
- **MIDI-out triggers:** zone entry, action start, and per-pose steps (each pose an action
  advances to). Continuous joint→CC and command-driven sends are **out of scope** this round.
- **`sound.json`** is a separate file (not bundled in `zones.json`), edited via a
  **dedicated sound section in `editor.html`** (form UI), saved over `/api/sound`.
- **MIDI-in:** `goto_zone` finds a shortest path on the zone `exits` graph (rejects if
  unreachable); `play_action` is added with an action-index CC mapping.
- `sound.json` **hot-reloads** like `zones.json` (`RELOAD_SOUND` / `SOUND_CHANGED`).

## Current state (facts)

- **`sound/sound.py`** (MIDI-out) already exists: `ZONE_NOTES` (zone→note) and `MODE_CCS`
  (mode→CC), hardcoded. On each `SNAPSHOT` it detects zone/mode changes and sends
  note-on/off + CC via `rtmidi.MidiOut`. Wired in `main.py`:
  `make_sound(bus, enabled=cfg.enable_sound, out_port=cfg.midi_out_port,
  out_device=cfg.midi_out_device)`; `--no-sound` disables; degrades to logging when no
  device / no `rtmidi`.
- **`io/midi.py`** (MIDI-in) maps: CC1(1-6)→`goto_zone`, CC2→`set_mode`, CC13→`set_flag`,
  CC20/21/22→`adjust_limit`, CC30→`set_mode`, note ch1/ch2 61-64→`set_joint_pose`,
  ch3→`random_wrist`, ch6→`set_linear_pose`. **No `play_action`.**
- **`state/machine.py` `request_zone`** does a single transition (current zone's `exitpos`
  → target `startpos`, exit skipped if already in target safezone). It does **not** walk
  the `exits` graph — no multi-hop.
- **`core/engine.py`** drains `Cmd.RELOAD_ZONES` → `reload_zones()` (swaps machine/brain
  zones, publishes `ZONES_CHANGED`). `main.py` passes `zone_loader` to the engine.
- **`io/httpserver.py`** serves pages + `/api/zones` GET/POST (atomic write + reload).
  **`config.py`** has `midi_out_port`/`midi_out_device` (sound) and `zones_path`.
- **`editor.html`** already has a zone/action editor (add/remove/edit/enable, ghost
  stepping) with Save→`/api/zones`; loads `rtr3d.js`. **`client.html`** dims zone buttons
  that are not *direct* exits of the current zone.
- Snapshot (each tick) carries: `zone, mode, action, joint_pose, cart_pose, target_pose,
  speed, flags, moving`. The Sound adapter can detect zone/mode/action changes and
  target-pose changes from it.
- venv: `/home/kaos/.pyenv/versions/kukart` (Python 3.11). `rtmidi` is in `requirements.txt`.

## Tasks (ordered)

### 1. `sound.json` + loader + validation (sound.py data layer)

- Generate `realtimecontrol/rtr/sound.json` from the current `ZONE_NOTES` / `MODE_CCS`
  (one-time; keep them in `sound.py` as built-in fallback). Schema:
  ```json
  {
    "channel": 0,
    "zones":  { "<zone>":  { "note": 48, "velocity": 60 } },
    "modes":  { "<mode>":  { "cc": 70, "value": 32 } },
    "actions":{ "<name>":  { "start": { "note": 60, "velocity": 80 },
                              "poses": [ { "note": 62, "velocity": 70 }, ... ] } }
  }
  ```
  - A **MIDI message** is one of: `{note, velocity}` (note-on), `{cc, value}` (control
    change), `{program}` (program change). The adapter converts to bytes using `channel`.
  - `actions.<name>` is keyed by **action name** (global, not per-zone — simpler; per-zone
    action MIDI is a later extension). `poses` is a sequence; pose `i` sends
    `poses[i % len(poses)]` (wraps). `start` is optional; if absent, pose 0 is used on start.
- `sound/sound.py`: `load_sound_data(path) -> dict` (JSON + validation; raises
  `OSError`/`ValueError`) and `validate_sound_data(data)` (channel is int 0-15; zones/
  modes/actions are dicts; every message has a valid type + in-range values). `sound/
  __init__.py` exports them.
- `config.py`: `sound_path` (default `sound.json` next to `main.py`). `main.py`:
  `--sound` path flag; load at startup, fall back to built-in `ZONE_NOTES`/`MODE_CCS` +
  warning if missing/corrupt (same pattern as `load_zones_data`).

### 2. MIDI-out: make `Sound` data-driven

- `Sound.__init__(bus, sound_loader: Callable[[], dict], enabled, out_port, out_device)`:
  loads the mapping from `sound_loader()` at startup.
- Replace hardcoded `ZONE_NOTES`/`MODE_CCS` lookups with the loaded table (default
  channel from the table).
- `_on_snapshot(snap)`: detect and fire, in order:
  - **zone entry**: `snap.zone != self._last_zone` → send `zones[zone]` (note-on; note-off
    the previous zone's note first, as today).
  - **mode change**: `snap.mode != self._last_mode` → send `modes[mode]` (CC).
  - **action start**: `snap.action != self._last_action` (and not None) → send
    `actions[name].start` (or pose 0).
  - **per-pose step**: when `snap.mode == "action"` and `snap.target_pose` changed since the
    last snapshot → advance an internal pose index and send `actions[name].poses[idx]`.
    (Heuristic: the snapshot has no explicit pose index; a target-pose change in action mode
    is treated as the next step. Limitation noted; exact index tracking = later extension.)
- **Degraded logging:** when no MIDI-out device is open (sim / no rig), **log each message
  it would send** (e.g. `[sound] note ch0 48 vel60`) so the mapping is testable without
  hardware. Keep the existing graceful degrade (no `rtmidi` → disabled).

### 3. Hot-reload for sound (mirror zones)

- `core/commands.py`: `Cmd.RELOAD_SOUND = "reload_sound"`, `Event.SOUND_CHANGED =
  "sound_changed"`.
- `core/engine.py`: constructor takes `sound_reload: Callable[[], None]`; in the command
  drain, on `RELOAD_SOUND` call it. (Mirror `zone_loader`/`reload_zones`.)
- `Sound.reload()`: re-read `sound.json` via the loader; on failure keep the current table
  + log; on success swap the table and `bus.publish(Event.SOUND_CHANGED, <mapping name>)`.
- `display/display.py`: on `SOUND_CHANGED` send `{"type": "sound_changed"}`.
- `main.py`: pass `sound_reload=sound.reload` to the engine (and the loader to `Sound`).

### 4. HTTP: `/api/sound` GET/POST (`io/httpserver.py`)

- Mirror `/api/zones`:
  - `GET /api/sound` → current `sound.json` (read fresh; fall back to the running table +
    built-ins if the file is bad).
  - `POST /api/sound` → `validate_sound_data`; on success **atomic write** (`tmp` +
    `os.replace`) to `sound.json`, then `bus.submit(Command(RELOAD_SOUND))`. On failure:
    HTTP 400 + error, file untouched.
- Add a `sound_provider` (current running table) to the `HttpServer` constructor, mirroring
  `zones_provider`.

### 5. MIDI-in: `goto_zone` path-finding (state machine)

- `state/zones.py`: `Zones.find_path(from_name, to_name) -> Optional[List[str]]` — BFS on
  the `exits` graph; returns `[from, z1, ..., to]` or `None` if unreachable.
- `state/machine.py` `request_zone`: replace the single-transition logic with:
  - reject unknown / disabled zones (existing);
  - `path = self.zones.find_path(self.current_zone, name)`; if `None`, log + return False;
  - build steps by walking the path: for each hop `path[i] → path[i+1]`, append
    `zones[path[i]].exitpos` then `zones[path[i+1]].startpos`;
  - set `self._transition = {"zone": name, "steps": steps, "i": 0}`.
  - Note: this **always** routes through the graph (drops the old "skip exit if already
    safe" shortcut) — more predictable and always safe. The old direct-transition is the
    path-length-2 case.
  - `update()` is unchanged (advances one step/tick).

### 6. MIDI-in: `play_action` (`io/midi.py`)

- Add a CC mapping to start an action by **index** in the current zone: proposed **CC3**
  (value `i` → the `i`-th action, 1-based; `0` → clear action). Exact CC/value is a
  decision to confirm against the user's controller; keep it in a small table (like
  `ZONE_BY_CC1`) so it is easy to adjust.
- `play_action` sends `Cmd.PLAY_ACTION` with the resolved action name (looked up in the
  current zone's `actions`). No-op (log) if the current zone has no such action.
- `goto_zone` (CC1) now benefits from path-finding automatically (it already sends
  `Cmd.GOTO_ZONE`; the state machine now routes it).

## Edge cases / failure modes

- `sound.json` corrupt at startup → fall back to built-in `ZONE_NOTES`/`MODE_CCS` + warning.
- Bad `POST /api/sound` → 400, file untouched (atomic replace only on success).
- `goto_zone` to an unreachable zone (no path) → rejected (log, no transition).
- `goto_zone` during an in-progress transition → rejected (existing guard).
- `play_action` when the current zone has no actions / bad index → no-op (log).
- No MIDI-out device / no `rtmidi` → sound degrades to logging (testable), core keeps running.
- Per-pose MIDI is a target-pose-change heuristic; identical consecutive poses may skip a
  step (acceptable; exact index tracking is a later extension).
- HTTP port 8766 busy → server disabled (existing); WS 8765 still works.
